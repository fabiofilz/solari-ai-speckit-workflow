# Contract: `.ai-workflow.toml` Schema (v1)

Canonical filename: **`.ai-workflow.toml`**, at the consuming project's
root. Format: TOML, parsed with stdlib `tomllib` (research.md §4). Owned
and generated by ChatGPT/the orchestrator (FR-015); read-only from the
runner's, Claude Code's, and Codex's perspective during ordinary
implementation/review — none of them may silently modify it (constitution
Governance).

Full field reference: `data-model.md` → "Project Workflow Configuration"
and "Environment Contract". This file states the **contract rules**
governing how the runner treats the document as a whole.

## Schema versioning

```toml
[workflow]
schema_version = "1"
```

- `schema_version` **MUST** be present.
- v1 of the runner recognizes **only** `"1"`. Any other value (including
  absence) is a hard failure naming the supported version(s) explicitly.
- A future `schema_version = "2"` will define its own migration note per
  the constitution's Governance section; there is no implicit coercion
  between schema versions, ever.

## Required vs. optional vs. stack-conditional

- **Required** fields (data-model.md marks each one): missing or wrong-typed
  → hard failure.
- **Stack-conditional** fields (e.g. `environment.lockfile`) are required
  only when `environment.stack`'s registry entry declares them required;
  the readiness gate — not the config loader — is what ultimately decides
  whether an absent stack-conditional field is a problem, since some stacks
  genuinely have no lockfile concept.
- **Optional** tables (`environment.docker`, `environment.local_model`,
  `environment.os_dependencies`, `environment.env_vars`, `known_deferred`)
  are valid entirely absent. When present, their own nested fields become
  required for that table (data-model.md marks these as "required if table
  present").

## Validation behavior (research.md §5)

- All schema problems are collected and reported **together** in one
  failure — never stop at the first.
- Every reported problem names its exact TOML path (e.g.
  `environment.lockfile`), not just a table name.
- **Unrecognized keys or tables anywhere** produce a **warning** on
  stderr, never a hard failure — this keeps the schema additive/forward-
  compatible. A missing or malformed *required* field is always a hard
  failure regardless of this rule. This leniency is for **unknown keys**
  only — an **invalid value for a recognized field** (e.g.
  `[git.push] mode = "auto"`, which v1 does not support) is always a hard
  failure, since the field itself is known and its accepted value set is
  fixed for this schema version.
- Parse errors (`tomllib.TOMLDecodeError`) are reported with the file path
  and the parser's own line/column position, unmodified.

## Ownership contract

- The runner **never writes** this file. There is no "runner writes back a
  normalized/updated config" behavior in v1, at all.
- Claude Code and Codex may **read** this file to understand project
  policy (build/test/lint commands, checkpoint policy, etc.) but **MUST
  NOT** edit it during ordinary implementation or review; a perceived need
  to change it is reported to the orchestrator, never applied unilaterally
  (constitution Principle I / Governance).
- `solari-workflow init` (`contracts/cli-interface.md`) is the only runner
  code path that ever writes this file, and only when it does not already
  exist (or with an explicit `--force` after showing a diff).

## Secrets

- `environment.env_vars` entries **MUST** contain example/placeholder
  values only. The readiness gate's common-checks section runs a
  best-effort heuristic scan (pattern-matching common secret shapes, e.g.
  `sk-...`, `AKIA...`, high-entropy strings) over config string values and
  flags anything suspicious — documented explicitly as a heuristic, not a
  guarantee, since no static scan can prove absence of secrets.
- Actual secret values are never read, logged, or embedded in `.ai-runs/`
  by any part of the runner.

## Example (minimal, Python stack, no Docker, no local model)

```toml
[workflow]
schema_version = "1"
source = "https://github.com/fabiofilz/solari-ai-speckit-workflow"
version = "1.0.0"

[project]
name = "example-service"
type = "service"
main_branch = "main"

[speckit]
spec_dir = "specs"

[environment]
stack = "python"
runtime_version = "3.12"
dependency_manager = "uv"
manifest = "pyproject.toml"
lockfile = "uv.lock"
lockfile_must_be_committed = true

[build]
test_command = ["uv", "run", "pytest"]

[git]
checkpoint_merge_strategy = "no-ff"

[git.push]
mode = "manual"   # v1 supports only "manual" — see research.md §0.2

[checkpoint]
tag_prefix = "checkpoint"
blocking_severities = ["blocker", "major"]

[branch_retention]
keep_recent_merged = 2
keep_active = true

[ai_runs]
directory = ".ai-runs"
git_ignored = true
```

No `[environment.docker]` or `[environment.local_model]` table is present
— the readiness gate reports both sections `SKIPPED`, never `FAIL`
(FR-021, SC-006).
